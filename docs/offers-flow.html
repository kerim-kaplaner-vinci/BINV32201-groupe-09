Gesta · architecture applicative

Du composant React à la base de données

Ce document retrace le parcours de lecture qui affiche les offres de stage. Le navigateur ne lit jamais SQLite directement : chaque couche délègue la responsabilité adaptée à la couche suivante.

Vue d'ensemble du projet

Le projet est organisé en deux workspaces npm. frontend/ est une application React/Vite : elle gère les pages, l'état de chargement, la navigation et l'affichage. backend/ est une API Express : elle authentifie l'utilisateur, applique les règles métier et interroge SQLite avec better-sqlite3.

En développement, le frontend appelle /api/.... Le proxy Vite retire /api et transmet la requête à l'API sur le port 3000. Le serveur backend est assemblé dans app.ts et ses dépendances sont créées par des fonctions factory.

1. Parcours côté frontend

OffersPage.tsx

La page reçoit l'utilisateur, le jeton et la fonction de déconnexion. Elle appelle useOffers(token, onUnauthorized). Elle n'applique pas elle-même la visibilité : le profil sert seulement à afficher la description de la liste, tandis que le backend reste l'autorité.

useOffers.ts

Le hook déclenche un effet lorsque le jeton change. Il crée un AbortController, appelle le service, met à jour offers, isLoading et error, puis annule la requête lors du démontage. Une réponse 401 déclenche onUnauthorized.

offers.service.ts et utils/api.ts

Le service appelle GET /api/offers avec Authorization: token, sans préfixe Bearer. readJson vérifie le statut HTTP puis le type du JSON avec isOfferList. Une réponse mal formée est donc rejetée plutôt que d'être affichée comme si elle était valide.

OfferTable.tsx

Le tableau reçoit la liste déjà filtrée et affiche le titre, l'entreprise, l'année, la période et le statut. Les codes de stockage comme P1, P2 et OTHER sont convertis en libellés français par utils/labels.ts.

2. Parcours côté backend

Authentification et autorisation

Dans app.ts, la route /offers est placée derrière authenticate. Le middleware lit le jeton brut, recharge l'utilisateur et ses rôles depuis la base, puis place l'utilisateur dans req.user. La route applique ensuite authorize(canListOffers) : un contact sans rôle de déposant reçoit 403.

offers.controller.ts

Le contrôleur ne contient pas la règle de visibilité. Après l'autorisation, il récupère l'utilisateur courant, appelle offersService.listOffers(user), convertit chaque résultat avec toOfferDto et renvoie le tableau JSON.

offers.service.ts

visibilityFilter traduit le profil en filtre de données : l'administrateur voit tout, l'étudiant voit les offres PUBLISHED, et un déposant voit ses propres offres. Le service convertit ensuite les lignes brutes en objets métier avec toOffer.

offers.repository.ts

Le repository contient la requête SQL préparée. Elle joint offers à companies, academic_years et periods, puis applique les paramètres de statut et de déposant. Le tri utilise la date de début de l'année académique puis la date de création de l'offre. 

WHERE (@status IS NULL OR o.status = @status)
  AND (@depositorContactId IS NULL
       OR o.depositor_contact_id = @depositorContactId)
ORDER BY ay.start_date DESC, o.created_at DESC

SQLite et mapping

Le schéma de 001_initial.sql relie chaque offre à une année académique et à une période via une clé étrangère composite. Le repository renvoie un OfferDbo, toOffer crée l'objet métier, puis toOfferDto expose uniquement les champs nécessaires à la liste frontend.

3. Fichiers concernés par un filtre par période

Le filtre doit être appliqué dans le backend pour ne pas contourner les règles de visibilité. Le frontend ajoute seulement le contrôle et transmet le choix.

Frontend : contrôle et état

frontend/src/pages/OffersPage.tsx : ajouter un select ou des boutons de période et transmettre la sélection au hook.

frontend/src/hooks/useOffers.ts : accepter period, relancer le chargement quand il change et l'envoyer au service.

Frontend : requête et types

frontend/src/services/offers.service.ts : encoder la période dans la query string, par exemple ?period=P1.

frontend/src/models/offer.ts : réutiliser PeriodCode ou ajouter le type du filtre si l'API distingue une absence de filtre.

frontend/src/utils/labels.ts : compléter le libellé du contrôle si nécessaire.

Backend : validation et contrat

backend/src/controllers/offers.controller.ts : lire et valider le paramètre unique (P1, P2 ou OTHER), puis le passer au service.

backend/API.md et backend/http/ : documenter le paramètre et les erreurs 400.

Backend : métier et SQL

backend/src/services/offers.service.ts : conserver la combinaison du filtre de période avec la visibilité liée au profil.

backend/src/repositories/offers.repository.ts : ajouter periodCode au filtre et à la clause SQL sur p.code.

backend/src/models/offer.ts : étendre OfferFilter côté repository si le type y est centralisé.

Tests

backend/tests/offers.test.ts : vérifier P1/P2/OTHER, paramètre invalide, combinaison avec chaque profil et absence de fuite d'offres.

frontend/tests/OffersPage.test.tsx : vérifier le contrôle, la requête envoyée et les états de chargement/erreur.

Exemple de circulation du filtre

OffersPage
  → useOffers(token, onUnauthorized, "P2")
  → getOffers(token, signal, "P2")
  → GET /api/offers?period=P2
  → controller : validation de "P2"
  → service : visibilité du profil + periodCode = "P2"
  → repository : AND (@periodCode IS NULL OR p.code = @periodCode)
  → OfferDto[] → OfferTable
